# Barracuda CGF Event Handling

These scripts help inspect or act on events generated by Barracuda CloudGen Firewall (CGF). They can be configured as an **Execute Program** action in CGF notifications. Available event fields and their names depend on the CGF version and configuration.

## Scripts

| File | Purpose |
| --- | --- |
| `dump_event.py` | Python 2.7 version that writes the process environment as JSON to standard output and `/tmp/barracuda_event_dump.json`. |
| `dump_cgf_event_environment_to_json.p3.py` | Python 3 version of the environment-dump script. |
| `event.py` | Reads an IPv4-shaped value from `EVENT_DATA` and can add it to a configured CGF network object through the REST API. |
| `add_event_ip_to_cgf_network_object.p3.py` | Python 3 copy of `event.py`; both files are currently identical. |

The two event-processing scripts use an external JSON configuration, defaulting to `/etc/barracuda-event-forwarder.json`. See [`event-forwarder.json.example`](event-forwarder.json.example) for its structure. Set `BARRACUDA_CONFIG` to use another path.

Create a private configuration file on the firewall, replace the example object names and credentials, and restrict access:

```bash
sudo install -o root -g root -m 600 event-forwarder.json.example /etc/barracuda-event-forwarder.json
sudoedit /etc/barracuda-event-forwarder.json
```

The configuration requires the fields shown in the example. Do not commit real credentials. The `event-forwarder.json` filename is ignored by Git in this directory.

### Dumping an Event Environment

`dump_event.py` and `dump_cgf_event_environment_to_json.p3.py` serialize the entire process environment to JSON. Configure **Execute Program** in CGF notifications and provide the full script path. For example:

```bash
python3 /path/to/dump_cgf_event_environment_to_json.p3.py
```

A manual run will not reproduce the environment variables supplied by CGF. Each run overwrites `/tmp/barracuda_event_dump.json`. The dump contains the **entire process environment**, not just event fields, and may include sensitive values. Use it only for controlled diagnostics, restrict access to the output, and remove it when finished.

### Adding an Event IP to a Network Object

`event.py` and `add_event_ip_to_cgf_network_object.p3.py` perform this workflow:

1. Read `EVENT_DATA`, `EVENT_TYPE_ID`, and `EVENT_TYPE_NAME` from the process environment.
2. Search `EVENT_DATA` for a dotted-quad pattern inside parentheses. The pattern does not validate that each octet is in the IPv4 range. If no matching pattern is found, the script makes no configuration change.
3. Read the exclusion object through the REST API and skip an address matching an exact IP or CIDR entry.
4. Check whether the exact address is already in the target object.
5. If not excluded or already present, submit it to the target object with the event type name as its comment.

This does not forward the full event or send it to a webhook; it modifies a CGF network object that can be used by firewall rules or other workflows. The target and exclusion object names, API address, and credentials must be configured for the deployment. The example object names are placeholders, not required CGF names.

## Security and Operational Notes

- Keep the API token and Basic Authorization value in a private configuration file outside the repository, with access limited to the account running the script. Revoke and replace any real credentials previously committed or exposed.
- The event scripts create an unverified TLS context for HTTPS requests. The example uses HTTPS, but certificate verification is disabled; use only on a trusted network until the code is changed to verify the server certificate.
- Event type and full `EVENT_DATA` are written to the log on every run. Additional object details are logged when `debug` is enabled. Protect logs because they may contain addresses and other event data.
- If reading the exclusion object fails, the script logs the error and returns an empty list; processing may continue without confirming the exclusion list. A failed read of the target object also prevents reliable duplicate detection. Review this fail-open behavior before using the script for automated blocking.
- Before use, configure valid target and exclusion objects, confirm the actual `EVENT_DATA` format for selected event types, and test against a non-production CGF environment.
